## V93：修「新建」时好时坏 + 创建后桌面自己刷新 + 改名框丢失（用户 10-10 三条报障）

用户原话：「第一次我创建成功，但是第二次创建就失败了，过了一会又第一、第二次成功，第三次不成功了」
「我创建文件夹后桌面自己刷新了，跟正常的桌面行为不一样」「我创建后应该聚焦到命名上，现在刷新，重命名都没有了」

### 根因（日志取证，两条）
1. ★★ **`label_editing()` 判据是错的**：`FindWindowExW(list, .., "Edit", ..)` 找的是
   `SysListView32` 的**常驻** Edit 子窗（控件创建时就有），**几乎恒为真**。V92 把它接到
   25ms 轮询上 ⇒ 每 50ms 往隐藏 view 投一条 `LVM_CANCELEDITLABEL`（日志实测 138 条）
   ⇒ 正好打断 Explorer 的 ShellNew 流程 ⇒「第一次成、第二次败、过一会又成」；
   同时频繁投递让 Explorer 重绘桌面 ⇒「创建后桌面自己刷新了」；取消了又没人接上 ⇒「重命名没有了」。
   正确判据：**`LVM_GETEDITCONTROL`（0x1018）** —— 仅编辑态才返回编辑框句柄。
2. **新建后走全量 `syncDesktop()`**：`grid:desktop-changed` → `syncDesktop()` →
   `gridDesktopSync()` + `refresh()` + `fetchLoose(true)`（竖条变宽 → `relayoutSoon()`
   120ms 后 `refresh()`）⇒ 整层 DOM 重建 ⇒ 刚 autoFocus 的改名框被卸载。
   而且 V92 前端**根本没有**「新建后开始改名」这一步（那条路只在**我们自己菜单**的
   `created !== null` 分支里），所以穿透路径下用户永远等不到改名框。

### 修法
- Rust：`label_edit_control() -> Option<HWND>`（用 `LVM_GETEDITCONTROL`），`label_editing()`
  改为它的布尔视图；取消动作加 **`EDIT_CANCEL_STAGE` 闩锁 + 400/800ms 有限升级**
  （`LVM_CANCELEDITLABEL` → `Esc` 投给编辑框本身 → `WM_CANCELMODE` → 收手留日志），
  **只在接管态才动**（没接管时那个框是用户自己在用的）；签名轮询 `% 8` → `% 4`（≈100ms）。
- 前端：新增「**改名 / 新建安静期**」—— `renamingRef` + `quietUntilRef` +
  `pendingRelayoutRef` / `pendingRefreshRef`（**重排与刷新分开记，重排优先补跑**）；
  `relayoutSoon` 与 `syncDesktop` 在安静期一律挂起；`grid:desktop-changed` 改走新的
  `onDesktopChanged`（**只增量**：`fetchLoose` + diff，**唯一新增项**就 `setFocus()` +
  `beginItemRename` 就地改名）。

变异自检 1 守卫 / 16 破坏用例全捕获 · 打包 `--no-deploy` ✓ · 归还桌面图标 →
